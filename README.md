# AppDock

AppDock is a native Windows 11 application launcher built with C#, .NET 10 and WPF. Containers hold references to applications; removing a reference never uninstalls or deletes an application. No third-party runtime icon packages, account or telemetry.

## Build and launch

Requires Windows 11, a .NET 10 SDK compatible with `global.json`, and the .NET 10 Windows Desktop Runtime. The solution and internal project/namespace names remain AppBox for source compatibility.

```powershell
dotnet build AppBox.sln -c Release
.\src\AppBox.App\bin\Release\net10.0-windows\AppDock.exe
```

Keep the entire build output together. `AppDock.exe` is the official executable. `AppBox.App.exe` forwards its arguments to the adjacent `AppDock.exe` so existing shortcuts continue working when upgrading in place. No installer or release archive is generated by this workflow.

## Containers

Open Settings from the notification-area icon, then **Containers**. Create, rename, delete (with confirmation), activate/deactivate, edit applications, or change an icon. Each row displays its icon, name, application count and activation state. Empty containers can be activated. Deactivation preserves apps, order and icon choices.

In **Single AppDock** mode the main launcher displays active containers with their selected icons. Click one to open its applications. In **Multiple AppDocks** mode each active container has a persistent shortcut with `--container <guid>` arguments. The original `--folder <guid>` alias remains supported.

Normal container popups contain application icons and optional application names. Left-click launches immediately and dismisses the popup when Auto close after launching an app is enabled. Failures use a nonblocking notification-area balloon (subject to Windows notification settings). Windows security prompts remain under Windows control. Click outside or press Escape to dismiss.

Right-click empty container space to edit, add applications, rename, change the icon, open container settings, activate/deactivate or close. Right-click a container tile in the Single launcher to select its management target. Right-click an app to launch, rename, open its file location where available, or remove its reference.

Edit Mode stays open during focus changes. Drop `.exe`, `.lnk`, or HTTP/HTTPS `.url` shortcuts from Explorer; drag existing icons to reorder. Use **Done** to return to normal launching. Changes save automatically; drag/edit state is transient. Settings controls application names, icon size, animations, theme and taskbar layout.

## General Settings and official branding

General follows the approved reference: a compact icon sidebar, two full-card layout selectors with graphical taskbar previews, and four row-wide toggle switches. Single/Multiple selection uses the existing layout setting and preserves containers, activation states, applications and custom icons. Multiple mode creates shortcuts; pinning still requires the Windows Pin to taskbar action.

**Other Options** controls Show app names, Auto close after launching an app, Start AppDock with Windows, and Use Windows 11 style (rounded corners, Mica effect). Changes save automatically; failures restore the prior preference and show an inline error. Startup uses the existing current-user registration service; the Startup page mirrors the same setting. Application icon size is now on Appearance. Navigation remains General, Containers, Appearance, Taskbar, Startup and About; the Taskbar page retains all Phase 2B interaction controls.

On supported Windows 11 builds, the style option requests rounded corners and the documented system backdrop through DWM, verifies API read-back, and enables the required WPF transparent client surface. Windows may render its own solid fallback depending on system conditions. If unavailable, AppDock uses the normal theme surface and explains the fallback; the full option is disabled on Windows versions that lack the supported backdrop API. Layered floating popups use AppDock's own corner/pointer rendering rather than claiming a DWM Mica backdrop. Settings fits the target monitor's working area; constrained layouts scroll instead of losing controls.

The official supplied AppDock artwork is compiled into the executable (16–256 px ICO), embedded for WPF windows, and included as 32/64/128 px PNG branding resources for Settings, About and previews. A persistent external `AppDock.ico` is copied beside the executable for Windows relaunch/shortcut resources. The default `Launchers/AppDock.lnk` uses the main stable AppUserModelID and the official icon. Application Jump List command icons use official branding; container launchers keep their own icons. No runtime path references the original `AppDock_Icon_Pack` directory. The original source pack is left intact and ignored by Git; necessary project resources are tracked.

Windows may cache the previous product icon for existing pins. Close the old instance, start the rebuilt executable, and manually unpin/repin the main AppDock shortcut if the old icon remains. AppDock does not edit taskbar caches or Explorer internals.

## Container icons

**Change Icon** offers eight **Default Icons**, **Choose Custom Icon**, **Reset to Default**, and a live preview. Local `.ico`, `.png`, `.exe`, and `.lnk` files are supported. Executable and shortcut icons are extracted by Windows Shell APIs without launching them. Transparency is retained. Built-in icons are drawn locally, with a generic AppDock container fallback.

Custom sources are decoded and copied into content-addressed `.ico` files under `%LOCALAPPDATA%\AppDock\Icons\`; the original file can subsequently move or disappear. Generated icons contain 16, 24, 32, 48, 64, 128 and 256-pixel frames. A missing or corrupt managed icon falls back to the generic icon without deleting the saved choice. Resetting changes only the icon definition, never the container GUID. Icons are retained when a container is deactivated or deleted so external pins do not acquire missing image references.

## Configuration and upgrading from AppBox

New installations use `%LOCALAPPDATA%\AppDock\settings.json`. If it does not exist and `%LOCALAPPDATA%\AppBox\settings.json` exists, AppDock copies the exact original bytes through a staging file before loading them. The legacy directory and its files are never deleted or rewritten. An existing AppDock configuration always takes precedence, including recovery cases. Copy/access failures stop startup with an error rather than starting from empty settings.

The schema version, `Folders`/application properties, GUIDs, application order and `SingleAppBox`/`MultipleAppBoxes` serialized enum names remain compatible. `IsActive`, `Icon` and `IconSize` are additive; legacy containers default to active with the generic icon and 48-pixel application icons. Saves use flushed temporary files, atomic replacement and a previous-revision `.bak`. Invalid configurations are copied to `settings.invalid-<timestamp>.json` before recovery.

Exit the old AppBox process before upgrading. Replace the output in its existing location and keep the compatibility executable beside AppDock. Existing shortcuts and pins that point to that location can then invoke the new app; arbitrary older installation paths cannot be repaired automatically. Existing AppBox startup registration is recognized. Explicitly changing the Startup setting switches the owned Run entry to AppDock and removes the old AppBox Run value to prevent duplicates. Old pins may keep their old label/icon until manually repinned. Legacy process IPC and the main `AppBox.Desktop` Windows identity are retained to avoid breaking existing grouping.

Launches retain path, shortcut argument and working-directory validation. Relative and remote executable paths, command interpreters and indirect command launchers remain unsupported. Packaged apps use validated Shell identities; `.url` references permit HTTP/HTTPS only. Configuration loading never executes targets.

## Taskbar Interaction and Jump Lists

Right-click a running or pinned AppDock taskbar icon to access **AppDock Settings**, **Edit Container**, and **Manage Containers** where Windows displays application Jump List tasks. Dedicated container launchers carry their stable GUID in each command. Settings/management commands select the relevant container; repeated requests reuse the same process and windows. The main Edit command uses the selected active container, or opens management if none exists. Inactive/deleted container edit requests fail gracefully. Existing `.lnk` paths, identities and legacy executable forwarding remain unchanged.

The documented `ICustomDestinationList` API publishes a separate task list for the main `AppBox.Desktop` identity and each `AppDock.Container.<guid>` identity. Commands may be launched directly:

```powershell
AppDock.exe --settings
AppDock.exe --manage-containers --container <guid>
AppDock.exe --edit-container --container <guid>
```

**Settings → Taskbar Interaction** includes Click, disabled/unavailable Hover and Click or Hover choices, reserved hover delays, **Show popup pointer** and **Enable popup animations**. Click remains the only enabled opening mode. Hover delays persist with safe limits, but no hover timer runs while hover support is unavailable. Loading a hover mode falls back to Click.

A small pointer is drawn as part of the popup's unified Light/Dark border and shadow. On a bottom taskbar it uses the cursor's horizontal position, clamped clear of rounded corners. When activation occurs away from the taskbar (for example, by keyboard or Jump List), it uses the popup center. This is approximate alignment, not an exact pinned-button location. Pointer geometry scales with DPI and the existing monitor/working-area placement. The pointer is hidden for top/side taskbar arrangements and can be switched off completely.

Reliable hover activation of independently pinned launchers was not established through supported APIs. DWM hover messages request thumbnails/live-preview bitmaps; notification-icon hover APIs apply to tray icons, not independent pinned launchers. UI Automation does not document a stable mapping from taskbar buttons to each container AppUserModelID, so AppDock does not guess from button names, poll Explorer, install global input hooks, or simulate interactive hover using thumbnails.

## Taskbar workflow

In Multiple mode, activate a container, open **Settings → Taskbar → Open Launcher Shortcuts**, and use Windows **Pin to taskbar** on its shortcut (or launch it and pin its running button). Shortcuts live under `%LOCALAPPDATA%\AppDock\Launchers\<guid>.lnk`. Names and icon changes update the same shortcut. Windows taskbar identities use the stable GUID, with matching window relaunch arguments and persistent icon resources.

Pinning is manual. Windows may cache a copied pin's icon or label; unpin and repin the generated shortcut when needed. AppDock never edits pinned taskbar files, Explorer's taskband registry, or undocumented taskbar internals. Deactivation/layout switching retain existing shortcuts and pins; invoking an inactive/deleted container reports that it is unavailable instead of opening a different container. The app presents one popup at a time, routed by each container launcher. Physical Windows pin grouping/cache refresh remains a manual acceptance check.

Positioning uses the pointer's monitor/taskbar edge, clamps to screen boundaries and accounts for DPI. Windows does not expose the exact pinned-button rectangle through the APIs used here.

## Validation

```powershell
.\scripts\validate.ps1 -Smoke
# Use isolated Release output while the normal build is running:
.\scripts\validate.ps1 -Smoke -Isolated
```

The smoke run uses isolated configuration and IPC, real WPF windows, Shell shortcuts, secondary-process IPC and a harmless test executable. Native Jump List tests use temporary diagnostic AppIDs and remove only those lists afterward. It renders Light/Dark captures into ignored `artifacts/smoke`; it does not pin anything or change startup registration.
